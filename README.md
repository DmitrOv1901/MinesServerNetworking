# MinesServerNetworking

Протокол клиент↔сервер 2D-MMO. Единственный источник истины: этот репозиторий
подключается сабмодулем и в сервер, и в клиент, поэтому копий кода протокола нет.

- Апстрим: <https://github.com/MinesReborn/MinesServerNetworking>
- Форк, в котором идут правки: <https://github.com/LexmarKKK/MinesServerNetworking>

Копия протокола в клиенте или сервере означает, что протокол гарантированно
разъедется. Правки идут здесь → PR в апстрим → мержа → **два отдельных bump'а
указателя сабмодуля** (сервер, клиент).

## Сборка

```
dotnet build          # MinesServer_Networking.slnx
dotnet test           # 363 теста, покрытие всех 109 зарегистрированных сообщений
```

ЦелевыеFramework'ы различаются по назначению, и это важно:

| Проект | Таргеты | Кто собирает |
|---|---|---|
| `MinesServer.Data` | `net9.0;net481` | оба |
| `MinesServer.Utils` | `net481;net9.0` | оба |
| `MinesServer.Networking` | `net481;net9.0` | оба |
| `MinesServer.Networking.Connection` | `net481;net9.0` | оба |
| `MinesServer.Networking.Connection.Client` | `net481` | клиент (Unity/Mono) |
| `MinesServer.Networking.Connection.Server` | `net9.0` | сервер |
| `MinesServer.Networking.Tests` | `net9.0` | CI |

**Расхождение поведения между `net481` и `net9.0` — не гипотеза, а найденный и
закрытый баг.** `IsValid` на ветке `net7+` использовал `IBinaryInteger.IsPositive`
(строго положительное), а на `net481` — `>= Zero`. Код 0 отвергался на `net9.0`,
из-за чего не декодировались `ClientHelloPacket` (рукопожатие) и
`OutdatedClientPacket` (отказ по версии клиента). Любая новая условная
компиляция обязана проверяться на обоих таргетах.

Схема решения — `MinesServer_Networking.slnx`. Классического `.sln` рядом с ним
нет намеренно: при двух файлах решений в корне `dotnet build` без аргументов
падает с `MSB1011`. `.slnx` поддерживается начиная с SDK 9.0.200.

## Кадрирование

Один кадр:

```
┌──────────────┬─────────────────────────────────────────────┐
│ int32 length │ payload                                       │
│              │  client: uint32 timestamp, uint8 code, data   │
│              │  server: uint16 code, data                    │
└──────────────┴─────────────────────────────────────────────┘
```

- `length` — **полный размер кадра вместе с самим префиксом**.
- Все числа little-endian.
- Кадр длиннее `ProtocolLimits.MaxFrameLength` (**4 МБ**) отклоняется как
  `PacketDecodeException`.
- Проверка длины живёт в `TryTake`, а не в `Put`: `Put` только складывает данные,
  кадр проверяется при попытке выделить его из буфера.

`PacketBuffer` намеренно zero-copy по `_buffer`, но `TryTake` возвращает
`byte[]` — аллокация на кадр есть.

## Коды пакетов: позиционные

Wire-код пакета — **его позиция в порядке вызовов `Register<T>()`** в статическом
конструкторе код-провайдера. Нигде не записан явно. Перестановка или вставка
вызова посередине молча перенумеровывает протокол, и падение приходит не в
тестах, а в игре: клиент декодирует payload не тем пакетом.

Пять независимых таблиц, каждая со своим namespace идентичности:

| Провайдер | Кодов | Что адресует |
|---|---|---|
| `RootClientPacketCodeProvider` | 26 | корневые клиентские пакеты |
| `ActionClientPacketCodeProvider` | 14 | игровые действия внутри `ActionClientPacket` |
| `RootServerPacketCodeProvider` | 50 | корневые серверные пакеты |
| `HBPacketCodeProvider` | 6 | события внутри RT-кадра `HBPacket` |
| `GUIComponentPacketCodeProvider` | 13 | компоненты серверных окон |

Снапшоты таблиц лежат в `MinesServer.Networking.Tests/CodeTables/`. Таблицы
продублированы в репозитории сервера (`MinesServer.Tests/Networking/`)
намеренно: пока они жили только там, протокол можно было сломать здесь, и падал
бы сервер.

Правило расширения: новый пакет добавляется **в конец** таблицы, иначе
перенумеровываются все последующие коды.

`IsValid` проверяет обе границы: код `0` валиден (первому зарегистрированному
пакету соответствует ноль), код `>= MaxIdentity` — нет.

## Сжатие

`LzmaPacket` (код 4) и `LZ4Packet` (код 40) — обёртки над произвольным
`IRootServerPacket`. Работают только в направлении server → client.

Формат обёртки: `[int32 uncompressedSize][сжатые данные]`, где
`uncompressedSize` — размер **фактически закодированного** префикса, то есть
`2 + Payload.Size`.

Ограничение `ProtocolLimits.MaxDecompressedLength` (4 МБ) проверяется **до**
аллокации. Механизм в двух обёртках разный, и смешивать их нельзя:

- **LZ4** — `MaximumOutputSize(declared)`, то есть объявленное значение
  **домножается** (`n + n/255 + 16`). Лимитировать надо сам заголовок.
- **LZMA** — размер идёт **напрямую** как `int32` из провода, мимо `Read4()`, и
  уходит в `outSize` `LzmaStream`.

Раньше обе обёртки сжимали мусорный хвост: LZ4 кодировал весь буфер, выделенный
под худший случай, LZMA — весь буфер из `ArrayPool.Rent` (он больше
запрошенного), а в заголовок писалась длина аренды вместо фактически записанных
данных. Round-trip проходил — хвост декодер игнорирует, — но каждый кадр
раздувался мусором, а заголовок не соответствовал содержимому.

## Контракт `IUnreliableLengthPacket`

Обычно декодер обязан восстановить `Size` ровно: иначе `PacketDecodeException`
(защита от дописанных в хвост байт). Пакеты, реализующие `IUnreliableLengthPacket`
(`LzmaPacket`, `LZ4Packet`, `HBPacket`), на это правило не распространяются: для
них проверяется `result.Size >= length`, потому что длина сжатого или
суммирующего контейнера не восстанавливается из payload.

Если новый контейнер не может восстановить свой размер, он **обязан** реализовать
`IUnreliableLengthPacket`, иначе он будет отвергнут на обеих сторонах.

## Соглашения кодирования полей

Кодек — `MemoryReader` / `MemoryWriter` из `MinesServer.Utils`.

| Правило | Пример |
|---|---|
| ASCII с префиксом `uint8` | `WriteU1PrefixedASCII` |
| UTF-16 с префиксом `uint8` | `WriteU1PrefixedUtf16` |
| UTF-16 с префиксом `uint16` | `WriteU2PrefixedUtf16` |
| массив с префиксом `uint8` | `WriteU1PrefixedArray` |
| массив с префиксом `uint16` | `WriteU2PrefixedArray` |
| хвост целиком | `ReadRemainingAsArray<T>` / `ReadRemainingAs*` |
| `[StructLayout(Sequential, Pack = 1)]` | `ProgramStatePacket`, `CellConfigurationPacket` |

Соглашения неоднородны: часть полей идёт через `MemoryWriter`-вызовы, часть —
blit-структурой через `UnsafeWrite`. Схемы и генератора нет.

**Правило хвоста.** Многие декодеры читают остаток кадра через
`ReadRemainingAs*`. Это позволяет дописывать новые trailing-поля без изменения
таблицы кодов, но правило нигде не закреплено: добавление поля в **середину**
структуры ломает wire, а добавление в конец — нет.

## Пустые пакеты

В протоколе **29** пакетов с `Size => 0`. Они делятся на четыре группы, которые
важно не смешивать:

| Группа | Кол-во | Это баг? |
|---|---|---|
| Серверные корневые | 5 | Нет. `CloseWindowPacket`, `HideClanPacket`, `ClearStatusPacket`, `DeselectItemPacket`, `OpenProgrammatorPacket` — семантически им нечего нести |
| Клиентские action-подпакеты | 10 | Нет. Координаты приходят из обёртки `ActionClientPacket(x, y, payload)` |
| Клиентские корневые, реализованные | 7 | Нет. Пустой payload компенсирован состоянием сервера |
| Клиентские корневые, no-op на сервере | 7 | Серверная работа, не протокол |

`Size => 0` — сознательный костыль: `Unsafe.SizeOf` пустой структуры различается
на Mono (Unity) = 0 и на .NET = 1, и wire-совместимость достигнута именно нулевым
payload. Это не семантика протокола.

**Модель владения программатором.** Список программ держит клиент
(`persistentDataPath/programmator.json`), сервер держит одну запущенную программу
на сущности игрока. Отсюда: `SaveProgramPacket` несёт `ProgramId`, `Start` /
`Pause` / `Stop` / `Step` адресуют единственную запущенную программу и
`programId` не требуется, а `Delete` / `Rename` — локальные операции клиента.

## Ошибки декодирования

`Decode` может бросить `PacketDecodeException`. Транспорт обязан его ловить:

- `IConnection` объявляет `event Action<Exception> OnError` и
  `int DecodeErrorCount`.
- Обе `TcpConnection` (клиент и сервер) оборачивают `Decode` в `try/catch`,
  увеличивают счётчик, поднимают `OnError` и **продолжают цикл**.

Продолжать, а не выходить, обязательно: кадр к этому моменту уже потреблён
буфером, и выход из метода отбросил бы все кадры, уже лежащие в буфере.

Решение «дисконнект или терпеть» принимает хост, а не библиотека: у клиента и
сервера политика разная.

## Чего в протоколе нет

Это не список недоделок, а описание границ. Каждый пункт закрыт отдельным
решением, а не багом.

- **Никакого шифрования.** Ни TLS, ни симметричного шифра, ни nonce, ни обмена
  ключами, ни HMAC, ни подписи. `AuthTokenPacket` и `HardwareFingerprint` из
  `ClientHelloPacket` едут открытым.
- **Нет reconnect-токена.** `ReconnectPacket` — единственный сигнал resume;
  механизма возобновления сессии нет, хотя `ClientHelloPacket` несёт
  `AuthToken`, который мог бы им быть.
- **Нет request ID / sequence / revision.** Ни в одном действии. Клиент шлёт
  `(uint)DateTimeOffset.UtcNow.Ticks` в `ClientPacket.Timestamp` — усечение
  100-нс тиков; циклически переполняется и не даёт ни дедупликации, ни
  причинной связи ответа с запросом. Подтверждение движения снимается **любым**
  `RobotPositionPacket` с совпадающим `BotId`, а не подтверждением конкретного
  шага.
- **Нет rate limiting и античита** — это ответственность сервера, не транспорта.
- **Нет схемы и генератора протокола** — описание только это.

## Модель угроз кадрирования

Без TLS и подписи поток открыт для MITM. Кадр в несколько байт, объявляющий
~2 ГБ, форсировал аллокацию соответствующего размера при распаковке. После
закрытия (`ProtocolLimits.MaxDecompressedLength`) такое отклоняется до аллокации.

Важное уточнение по направлению: обе компрессионные обёртки декодируются
**на клиенте, в направлении server → client**. Удалённый игрок на это повлиять
не может. Реальные эксплуатанты — MITM, некомпрометированный сервер или баг
компрессора.

## Структура

```
MinesServer.Data/                     перечисления и структуры домена (ProgramState, ProgAction, …)
MinesServer.Utils/                     MemoryReader / MemoryWriter, расширения Span
MinesServer.Networking/                пакеты, код-провайдеры, кодеки, IUnreliableLengthPacket
MinesServer.Networking.Connection/     PacketBuffer, IConnection, контракт ошибок
MinesServer.Networking.Connection.Client/  клиентский транспорт (net481, Unity)
MinesServer.Networking.Connection.Server/  серверный транспорт (net9.0)
MinesServer.Networking.Tests/          round-trip тесты, снапшоты кодов, негативные тесты
MinesServer_Networking/                консольный smoke-стенд
```

Каталоги заканчиваются на `~` намеренно: Unity не импортирует директории, чьё
имя заканчивается на `~`, поэтому артефакты сборки пакетов не засоряют проект
клиента. Пути вывода заданы в `Directory.Build.props`, а не в `.csproj`: SDK-style
проект подключается уже после `Microsoft.Common.props`, и свойство, заданное там,
переопределяет `BaseIntermediateOutputPath` слишком поздно (MSB3539), из-за чего
NuGet пишет вывод по старому пути.
